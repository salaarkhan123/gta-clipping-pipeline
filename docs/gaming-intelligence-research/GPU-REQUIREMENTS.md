# Hardware, inference budgets and operating cost

Start with CPU measurements on permitted media. A sparse HUD reader, transcript features and a numerical ranker can be tested before buying hardware. If a GPU-only experiment survives the quality gate, seek approval for a bounded rental, beginning with the L4. Escalate to a larger card only when a measured memory or latency constraint identifies the reason. There is no assumption of an owned GPU, no paid run in this study, and no measured ClutchClips GPU throughput.

## A workload that can be measured

1. Reuse the performance initiative's decode, timing, cache and ASR interfaces as they land. In the research harness, log the same input and source commit, decoded presentation timestamps, codec, source frame rate, resolution, audio availability, and cached artifacts. Hash prompts, model weights and inference settings. Use a whole-VOD baseline as well as a fixed candidate trace so a faster machine cannot appear to improve quality by silently sampling more frames. See the [architecture audit](CURRENT-ARCHITECTURE.md).
2. Sweep low-cost coverage at 0.5, 1 and 2 frames/s. At 1 frame/s an hour produces 3,600 sampled frames. A 60 fps recording has 216,000 frames/hour. Small objects need native-resolution crops even when the scene classifier uses a reduced image. Count frames decoded as well as frames sent to each model. Interframe codecs can require decoding frames that a model will never receive.
3. Compare a cheap overlay-change trigger with fixed sampling. In candidate windows, test 8 frames/s for 10 seconds around each hit. Twenty disjoint windows give 1,600 dense-window frame requests before deduplication. Budget CPU and GPU preprocessing, batch only same-shaped crops, and merge overlapping requests by source timestamp. Inspect a random sample of nontriggered windows and short-lived HUD events so missed triggers are visible.
4. Run OCR or a compact detector only when the relevant region changes. Test CPU FP32 and INT8 against GPU FP16 on identical crops, then vary batch size 1, 4 and 16 subject to memory. Quantization calibration uses separate development streams with small fonts and dim overlays. Measure exact-match event precision, recall and boundary errors after conversion. Keep the original precision when small-text recall declines past the preregistered tolerance.
5. Apply an expensive verifier only to a fixed quota of ambiguous intervals. Fix frame count, pixels, prompt tokens and maximum output length. Record queueing, decoding, tokenization, preprocessing, transfer, model forward, generation and output write. Schedule around ASR and rendering, or measure concurrent contention deliberately. Weight storage alone is a lower bound on VRAM because cache, activations, other processes and runtime workspace also consume it.
6. For each workload, repeat cold start and warm-cache runs over the same held-out VODs. Pin container, driver, CUDA/runtime versions, CPU threads, batch and concurrency. Report median and p95 across jobs, throughput in **source video hours per billed machine hour**, peak host RSS, allocated and reserved GPU memory, device-wide high-water mark, wall power, retries/OOM, and accepted highlights per dollar. Preserve a row for failed arms. Use the [evaluation framework](EVALUATION-FRAMEWORK.md) for quality gates.

## Cost per source video hour

For a batch, divide the sum of billed machine hours × each machine’s hourly rate, storage, external API charges, and any source-side data transfer charges by successfully processed source hours. Include the cost of idle reservations, cold starts, retries and failed jobs in the numerator. Attach host staging and render costs once. Show both incremental detector cost and the end-to-end invoice. Runpod’s current documentation lists no Pod ingress/egress fees and quotes $0.07/GB-month for network volumes under 1 TB. For example, a retained 100 GB volume for a month adds $7 before compute. [Pod billing](https://docs.runpod.io/pods/pricing)

Illustrative arithmetic at **15 billed machine minutes per source hour for each arm** gives C6 $0.040, RTX 4000 Ada $0.190, RTX 4090 $0.223, RTX 5090 $0.348, L4 $0.173 and L40S $0.273 before add-ons. This common input is a sensitivity assumption. Actual time may differ by orders of magnitude. At $1.09/hour, L40S must process more than 1.58 times as many source hours per billed hour as a $0.69/hour L4 to beat its compute cost at equal quality. The threshold for the $0.89/hour 4090 against L4 is 1.29 times.

## Renting against a dedicated workstation

For a price anchor, a Canadian retailer listed a PNY RTX 5090 at **CA$9,499 for the card**, and the product page showed it sold out. This is a dated example of acquisition uncertainty. Obtain a complete, available workstation quote before a purchase decision. [Canada Computers SKU VCG509032TFXPB1](https://www.canadacomputers.com/en/powered-by-nvidia/269045/pny-geforce-rtx-5090-triple-fan-gddr7-triple-fans-vcg509032tfxpb1.html)

Worked scenario in Canadian dollars. Assume CA$11,000 complete workstation net cost, 36 months, zero residual value, 0.65 kW at the wall while active, CA$0.20/kWh and CA$1.40 per US dollar. The FX and energy prices are hypothetical. Use the same 5090 workload locally and in a rental at US$1.39/hour. With equal throughput and a powered-down local host between jobs, monthly local cost is `11,000/36 + 0.13 × local active hours`. Cloud cost is `1.946 × billed cloud hours`. These calculations exclude tax, financing, staff, failures and cloud extras.

| Monthly active hours at equal throughput | Local CA$/month | Cloud CA$/month |
| ---: | ---: | ---: |
| 40 | 310.76 | 77.84 |
| 100 | 318.56 | 194.60 |
| 180 | 328.96 | 350.28 |
| 300 | 344.56 | 583.80 |

At equal throughput the crossover is about **168 busy hours/month**. More generally, let `s` be billed cloud hours required to finish the same work as one busy local hour. The monthly crossover in local hours is `(11,000/36) / (1.946 × s − 0.13)` when the denominator is positive. If cloud finishes the work in 0.75 hours, the crossover rises to 230 local hours/month. If cloud needs 1.25 hours, it falls to 133. Idle power, cooling, maintenance or financing increases local cost. Long cloud idle reservations, retry costs or data transfer increase cloud cost. A fair decision compares the least expensive configuration on either side that meets the quality and latency gates, including CPU-only.

**Approval decision.** First provide measured source hours/month, sustained utilization, quality delta, p95 latency, memory headroom, a current workstation quote, and the cheapest qualifying rental cost. Request a capped, time-limited pilot only if an untested GPU stage can answer a specific quality or throughput question. Revisit a purchase when measured demand, hardware availability and a conservative cost sensitivity support it.
